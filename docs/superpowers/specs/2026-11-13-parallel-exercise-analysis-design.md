# 习题分析与切分并行化设计

## 目的

巨型文档在 OCR 完成后，章节内容分析、题号切分和后处理按单个 Python 执行流进行。目标是缩短这段 CPU 密集流程的总耗时，同时保持章节顺序、题目内容、答案、页码、bbox 和公共 JSON 格式不变。

本设计按用户确认的优先级选择多进程：优先提速，允许增加内存占用。常规 CPython 的线程受 GIL 限制，不能可靠地使 `split_exercises` 这类 Python 逐行逻辑同时运行在多个 CPU 核上。

## 当前路径与可并行边界

- CLI `run_pipeline`：`build_sections` → `ocr_pages` → `combine_section_pages` → 按文档类型 `extract_exercises` → 全树答案匹配 → bbox → OSS → 输出。章节切分现在在单次树遍历中进行。
- 公共 PDF/图片 API `iter_sections`：答案节点先 OCR，然后按目录顺序逐节 OCR、拼页、切分和 yield；调用方可以提前停止。
- `split_exercises` 在一道题、共用要求、跨页和题号序列之间维持状态。因此不能简单按页或固定字数切块。
- 课本隐式节点需要父标题与整棵树的已知小节名；试卷文末答案匹配需要所有题型的结果；答案章节匹配、bbox 的块占用状态和输出顺序也依赖汇总后的结果。

## 考虑过的方式

1. **按章节使用线程池。** 改动较小，还可与读缓存、输出等 I/O 重叠；对主要由 Python 执行的切分不能保证多核加速。未选。
2. **按章节使用进程池。** 每个任务拥有独立解释器，能并行执行切分；需要传输章节文本和结果，并控制峰值内存。选用。
3. **按页或固定字数切块。** 任务数多，但会切断跨页题、共用要求、配图归属和题号序列。未选。

## 模块与数据流

在提取层建立一个内部的“单个语义区间分析”接口：输入仅包含该节点的 `exercise_content`、标题、父标题、边界元数据、文档类型及只读的已知小节名；输出为提取后的 `exercises`、审校原文等节点补丁，或“丢弃此隐式节点”。工作进程不接收整棵目录树，不写共享节点、OCR 缓存或输出文件。

主进程先完成目录识别、OCR 和拼页，随后按目录顺序建立任务。使用显式 `spawn` 上下文启动 `ProcessPoolExecutor`，避免在 PaddleOCR/底层线程初始化后 fork。提交窗口限制为 `2 × workers`；默认关闭多进程，CLI/API 必须显式启用。启用后，估算输入达到可配置阈值（默认 8 MiB）才启动进程池；`--analysis-workers` / API 同名参数配置最大 worker 数，默认取可用 CPU 数与 4 的较小值，`1` 使用顺序路径。不要把整本书的章节文本一次性排入进程池。

主进程按原树顺序接收结果并合并节点，维护隐式节点的移除规则。子进程异常附带章节路径抛回；停止后续提交并取消待处理任务，不把失败章节当空结果。合并完成后，原有答案匹配、bbox、OSS 和输出仍由主进程按原顺序执行。`review_concurrency` 是 LLM 审校并发，与 `analysis_workers` 独立。

CLI 可在整树 OCR 后同时分析多个章节。流式 API 则由主进程顺序 OCR、拼页并把已准备好的章节送入有界进程池；按目录顺序 yield，保证结果顺序与当前一致。生成器关闭时取消未开始的任务并关闭进程池，明确测试提前中断时的资源释放与残留运行任务。OCR 的同文档缓存锁仍保持原有串行生产，不在工作进程内运行 OCR。

对只有一个大节点的文档，先在主进程划出**已有的语义区间**：无目录习题集按真实小标题块，试卷按题型小节。各区间分别分析，最后按原顺序做题号整理、答案区匹配和输出。没有可靠小标题或题型边界时，保持整节点顺序分析；不按页强行拆分。`extract_exercise_from_markdown` 当前先全篇切分以辨别误识别标题，第一阶段保持其行为，待独立基准确认瓶颈后再设计安全分块。

## 实施次序

1. 为 OCR 后的拼页、章节切分、答案匹配、bbox 分别记录耗时和峰值内存，拿至少一份缓存完整的巨型文档做基线。`combine_section_pages` 当前反复做字符串 `+=`，先改为列表汇总后 `join` 并确认收益，避免把拼页成本误判成切分成本。
2. 把课本、带目录习题集的“单节点分析”从树遍历中抽出为无共享写入的内部接口；顺序路径先调用同一接口，验证结果等价。
3. 加入有界进程池、按序合并和可配置 worker 数；先覆盖 CLI，再覆盖流式 API。
4. 对无目录习题集和试卷增加语义区间并行。两者的跨区间归并和答案回填留在主进程。
5. 用 1、2、4 个 worker 在同一缓存数据上测总耗时、分析阶段耗时、峰值内存和 CPU 利用率；若进程通信或内存抵消收益，保留 `1` 作为回退配置。

## 正确性与验收

- `analysis_workers=1` 与并行模式的每节公共 JSON、Markdown、report 内容一致；只忽略日志与计时信息。覆盖跨页题、共用要求、图注、隐式节点丢弃、答案回填、bbox、试卷题型、无目录习题集。
- 章节返回和写出顺序保持目录顺序，异常不得静默丢题；流式迭代器提前关闭后不再产生输出。
- 用同一份已缓存文档重复测量，先报告各阶段占比，再报告端到端收益和峰值内存。单个无法安全切分的巨型章节需要明确报告为顺序处理，不能宣称多核加速。

## 约束与风险

- 进程池需要序列化章节文本与习题结果，worker 数过大会抬高内存；任务只传最小数据，并限制待处理窗口。
- `spawn` worker 必须导入纯分析模块，不能在子进程创建 PaddleOCR pipeline、打开同文档 OCR 缓存锁或执行 OSS 上传。
- Python 3.10 起的 `ProcessPoolExecutor` 无法可靠地立即中止正在运行的任务；流式关闭可取消排队任务，但正在运行的少量任务可能短暂完成。若实际需要强制立即停止，单独改用支持 `terminate` 的进程管理实现。
- 若瓶颈主要在 OCR、拼页或 bbox，分析阶段并行不会带来等比例的端到端收益；以基准测量决定是否继续扩展。
